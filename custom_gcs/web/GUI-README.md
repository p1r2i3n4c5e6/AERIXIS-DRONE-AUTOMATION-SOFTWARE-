# AERIXIS Mission Control — 6-step interface (revised 2026-10-22)

`index.html` is the interface (`ui/css/gcs.css`, `ui/js/*.js`, plain ES modules, no build step). `classic.html`
(BT drag-and-drop editor) is unchanged and linked at the bottom of the sidebar. No command or safety logic lives in
the browser.

Look (2026-10-22, from the user's reference): dark navy sidebar with coloured line icons (no numbers) and a glowing
card for the active workspace; every workspace and every card has its own colour (gradient edge, icon tile, header
wash), richer multi-colour gradients in dark mode; green/amber/red only for state. Light/dark switch in the top bar.

Brand (2026-10-22): the product is **AERIXIS** (all caps, as in the logo). Logo files in `ui/brand/`: the user's
original raster (`aerixis-logo-original.webp/.png`), clean SVGs traced from it (`aerixis-logo.svg` navy on light,
`aerixis-logo-dark.svg` light on dark, `aerixis-mark*.svg` the "A" alone, `aerixis-icon.svg` + `-512/-192.png` app icon,
`/favicon.ico`), regenerated by `tools/make_brand.py`. Sidebar brand tile = logo + "Mission control"; clicking it opens
About (with the credit: built on the open-source AeroStack2 framework, BSD licence — internal package names such as
`as2_*`, ROS topics and storage keys keep their old names on purpose).

Loading splash (`ui/css/splash.css`, `ui/js/splash.js`, markup at the top of `index.html`): the first thing on screen.
Frosted card, the logo settles in once (A rises, teal swoosh sweeps across, letters follow), then a slim bar tracks
the real steps reported by `main.js`: interface built, GCS server answers `/api/state`, `/api/fleet` polled (aircraft
+ link), mission catalogue loaded, maps (Leaflet present + one imagery tile probe; offline = amber "cached tiles only",
not a blocker). Fades into the app when all are done (min 2.2 s on first open, 0.35 s on reloads in the same browser
session). Error card with Retry / Open anyway if a step fails, a script does not load, the server stops answering
(8 polls) or after 25 s. Esc / "Open now" skips it at any time (emergency controls are never blocked). Toasts stay
visible above it. `/?splash=hold` keeps it up for checking its look. `start_gcs.sh` opens the GCS in a browser
window once the server answers (`GCS_OPEN_BROWSER=0` to disable), so the splash is what the operator sees first.

Notifications: bell in the top bar (unread count, history for the browser session, setting for onboard log-line pop-ups).
Toasts in the bottom-right corner (alerts.js) for: GCS offline, telemetry link lost, aircraft status lost, onboard abort,
mission failed/completed, new flight-controller faults/unhealthy sensors, battery < 30 %, GNSS lost in flight, separation
unsafe in flight, PX4 warnings, onboard log errors/warnings, GCS errors. In-flight emergencies open the full-screen Emergency
view (below). Leaving a step forward with unfinished items opens "Before you leave …" (Stay and fix / Continue). Start all
explains every blocker and offers "Reconcile on ground".

Restored from the classic UI, per aircraft (links.js): System architecture link (GCS → MAVLink → gateway → mission
manager → AERIXIS core → Micro-XRCE-DDS → PX4, plus A8 camera and mesh, each with live state), Local vehicle
status, Telemetry & mission data (upload/download KB, packets, rates per system ID, BT XML payload, heartbeat).
Shown on Connect (tab per aircraft), Operations drawer → Links & data, Logs → Links & data.
BT execution log (btlog.js): node changes per aircraft built from the status polls (no extra radio), shown in
Operations drawer → BT execution and Logs → BT execution. Assigned trees survive a browser reload (session).

## Swarm start, notifications, emergency, custom missions (2026-10-22 evening)

Files: `ui/js/preflight.js` (checks), `page-readiness.js` (Swarm start page), `emergency.js`, `alerts.js` (toasts),
`missions.js` (catalogue), `builder.js` (mission builder), `page-plan.js`; server `mission_store.py`, `server.py`,
`planner_bridge.features()`. Backups of the files as they were before: the session scratchpad `gcs_backup_orig/`.

**Swarm start** (step 2, hash `#ready`). Per aircraft, groups: Telemetry radio (GCS link, heartbeat of this system ID),
Gateway & mission manager (fresh status, no abort/lockout, flight allowed*, motion enabled*), AERIXIS core (core nodes,
vehicle healthy), Flight controller (XRCE-DDS data, PX4 arming checks, sensors, failsafe, battery ≥ 30 %), GNSS (3D fix,
quality*, jamming, position), Mesh (fleet only: peers fresh, separation), Camera (only if the selected mission detects
people; gimbal*), Payload (only if it drops: servo adapter, package confirmed*), FC guardian (when reported: ON_GROUND or
MONITORING*). `*` = optional, chosen in "Checks counted" (saved per browser); the rest always count. "n/a" groups do not
count. Ready = all counted checks pass, no recent PX4 error (< 60 s), no FC/AERIXIS-core fault, not flying; fleet ready also needs
the GCS server and the telemetry link. Same verdict drives the drone cards' READY and Upload's badge. No extra radio traffic.

**Notifications.** Flight data warnings/errors are toasts in the bottom-right corner (max 4, errors stay until closed or
20 s, never cover the screen) and are kept in the bell history. Onboard log lines from the aircraft become toasts too: bell →
"Onboard log lines as pop-ups" = errors + warnings (default) / errors only / off; at most one per aircraft every 4 s. GCS server
errors (e.g. emergency not acknowledged) also pop up. The "Before you leave …" step guard and Start-all blockers stay dialogs.

**Emergency.** Full-screen view opens by itself when an aircraft that is armed or executing has: onboard abort, PX4
failsafe, link loss (> 5 s, or telemetry heartbeat lost > 6 s), FC guardian acting (COMMANDING / EMERGENCY_ACTIVE /
PX4_FAILSAFE) or the AERIXIS core down, battery < 20 %, or a failed mission while armed; or from the red **Emergency** button in the top
bar (all aircraft listed). Per aircraft: reasons, armed/mode/altitude/battery/status age, **Return to launch** / **Land now**;
plus RTL all / LAND all. The mission's emergency setting is the highlighted button. Command state (sending n/5, accepted,
REFUSED, no acknowledgement) next to each aircraft. "Hide" (or Esc) keeps a red banner with "Open". A new reason reopens it.
Server: `POST /api/emergency {drone_ids: [..] | "all", action: "RTL"|"LAND", reason}` → MAVLink COMMAND_LONG
NAV_RETURN_TO_LAUNCH (20) / NAV_LAND (21), target = that aircraft's system ID, component 1 (the gateway hands it to the FC
guardian, which commands PX4 even with the AERIXIS core down; NAV_LAND to component 190 would be a normal AERIXIS land), confirmation =
retry count, every 1 s until COMMAND_ACK from that system, max 5; state in `/api/state.emergency[sysid]`. ACK 0 = accepted by
the FC guardian, 2 = "on ground, nothing to do", 4 = refused (guardian not running / no PX4 link). Guardian state comes
from the status poll (`links.guardian`) or, when the AERIXIS core/manager is silent, from the gateway's `LINK|GUARDIAN|UP|<state>
action=<A>[ emergency=<A> <state>]` / `LINK|GUARDIAN|DOWN|…` STATUSTEXT (`/api/state.guardian[sysid]`); `EMERGENCY|<A>|…`
replies go to the GCS log. The view opens when the guardian reports an emergency (source gcs or as2_loss; STOOD_DOWN =
pilot/other mode took over); PX4_FAILSAFE, NO_FC, WAITING_FOR_AS2 or guardian DOWN while airborne are error toasts. The
command does not cancel the BT; use Cancel in Operations if the mission should also stop.

**Custom missions.** Built-in missions 1–5: always listed, usable, "Edit a copy" (file icon); never deletable (server refuses
their IDs and names). My missions: stored by the GCS server in `config/missions/c_<id>.json` (operator choices only: feature
spec, parameter values, name, notes — never XML); edit, copy, delete; "Save values to this mission" stores the current
parameters. Builder: 1 Aircraft carries (camera, payload servo) · 2 Mission type (area coverage, watch stations, track
person) · 3 When a person is found (detection, geotag, payload drop, orbit radius/laps, continue searching) · 4 Finish &
safety (RTL / land in place at the end and on emergency, name). Impossible choices are disabled with the reason; the right
panel shows the planner's own description and needs (`/api/missions/describe`). The planner
(`as2_rescue_planner/features.py`) builds the tree with the mandatory safety parts, shown locked in step 4. Planning a
custom mission sends `template: "custom", features`; every mission sends `emergency_action`, which also goes onboard with
Upload (stage request) for the FC guardian. A mission without camera needs no camera in Swarm start.

Radio budget (measured in SITL, 2 drones idle): 1.7 KB/s total (was 49 KB/s). Status polls are deltas
(`/api/status?lite=1&log=…&bt=…&ros=…&st=…`, merged back in `fleet.py`), 1 s while flying / 2.5 s idle; gateway
position telemetry 2 Hz (`telemetry_rate_hz`); ROS log relay limited to the drone's own nodes, ~1 line/s, repeats
suppressed; planner XML is compact (~2 KB = ~9 radio frames per drone).

Multi-drone SITL: `./3_launch_simulation.sh N` then `DRONES=N rescue_ws/scripts/sitl_onboard.sh "x,y;x,y"`; the
gateways sit behind `sitl_radio_hub.py` (one multipoint radio, `--stats` prints bytes per MAVLink message).

# Hybrid GCS interface

## Main project integration

The complete interface is installed in `/home/prince/custom_gcs/web`. The existing `start_gcs.sh` launcher runs the original `server.py`, which serves this folder and the existing API together at `http://localhost:8765`. Launch from the main project with `bash start_gcs.sh`, then refresh the browser. Port 8876 was a static design preview; use port 8765 for backend-connected operation. No separate frontend server or build step is needed to run the checked-in GUI.

`index.html` loads the bundled interface and all display modules. `css/crystal.css` is the final visual layer: black/navy navigation, pale workspaces, translucent glass cards, deeper multicolor edges and readable headings. It overrides the earlier palette layers. Existing controls retain their command handlers; fleet execution, link activity, notifications and map presentation receive data from the existing refresh paths.

Integration verification on 2026-10-21 exercised the original server's static handler without starting radio connections: the entry page and all 32 local stylesheet/script assets matched the installed files. All 18 JavaScript files passed syntax checks; execution-state/completion and GPS-validity checks passed. All 12 backend, bridge, package and launcher hashes matched the pre-GUI baseline. These checks do not constitute a live hardware flight test. The GPS telemetry limitation below still applies.

Dark navigation and execution canvases accompany light planning surfaces. Mission Builder contains setup, routes/swarm and tree review; there is one planning destination in navigation. Desktop workspaces use available viewport height. Long lists remain accessible through local scrolling; the topology canvas uses fit/zoom/pan instead of nested scrollbars. Narrow screens stack working panels. Motion respects reduced-motion preferences.

## Live execution
execution-model.js interprets fresh fleet snapshots. live-execution.js receives those snapshots through a guarded UI hook at the beginning of the existing Fleet render function. There is no additional polling and no command path. selectAircraft exposes the existing GUI selection function for the monitor selector. All transport, command and safety gating code is unchanged.

The Live execution workspace displays action results and a full hierarchy. Running highlights require fresh telemetry, active execution and a RUNNING node status. SUCCESS/FAILURE/SKIPPED come from the executor; IDLE nodes retain explicitly reported results. Stale telemetry removes running highlights and shows UNKNOWN. Counts describe reported action results, not elapsed time or an estimated mission percentage. Alternate/skipped branches are not marked successful just because the overall mission succeeded.

Completion notifications require a fresh explicit SUCCESS, inactive execution and a finite finished_at, for a run observed active in this browser. Identity combines aircraft, mission, revision and command/start identity. Historical success does not popup on opening the GCS. Completion popups remain until dismissed (up to four visible notices). Notifications are deduplicated per run with session storage; no physical delivery or all-swarm completion is inferred from a tree result.

## Graphs
flow-canvas.js draws the designer and onboard networks. Graph drawing, selection, collapse and zoom do not change XML. Designer data model, templates, validation and import/export remain unchanged.

## Validation
Node-state/completion unit checks cover stale reports, historical success, repeats, different runs, failures, cancellation, interruption and missing final acknowledgements. An isolated HTTP fixture exercised actual UI polling and running-to-success updates, including action highlighting and completion notifications. The fixture rejects commands and is labeled SIMULATED TELEMETRY. No aircraft commands or live flight tests were performed.

Backend checksums and source comparisons verified the command/transport logic is preserved. The only Fleet additions are a guarded read-only display hook and an existing GUI selection function export.

## Industrial palette and aircraft viewers
industrial.css supplies neutral graphite/pearl surfaces and restrained cyan, blue, violet, amber and coral accents. Green is reserved for reported success/healthy states. task-icons.js supplies local SVG icons; task types and execution states have separate styling.

Both editor and live network flow from top to bottom. The shared flow renderer saves zoom, pan and collapsed groups per aircraft/run (up to 40 contexts per canvas). The live viewer also saves inspector and action/tree mode per aircraft/run. Fleet status cards and the selected aircraft header provide direct View BT links. No graph selection, view switching or animation sends a flight command.

Verification used labeled, command-disabled telemetry fixtures for three aircraft. Collapsing the first aircraft left the third aircraft's seven-node tree intact; returning restored the first view. Independent zoom was verified. Backend and operational-source comparisons passed. No actual aircraft operation was tested.


### Warm contrast and communication feedback

`css/contrast.css` adds charcoal workspaces, warm stone glass and restrained copper, plum, teal and amber accents. Text contrast is increased across fleet, mission builder, tree viewer and dialogs.

`js/link-transfer.js` adds the Links & data panel. It consumes the existing `/api/state` and fleet refreshes through isolated, guarded display callbacks; it creates no network requests. Local MAVLink TX/RX rates and packet totals are kept distinct from fleet onboard connection status. Directional packet animation requires a fresh connected local state and a positive reported rate. Failure or a 3.5-second local update gap stops traffic animation. The waiting state describes an unconfirmed heartbeat, not a completed connection.

Aircraft XML uploads show an indeterminate pending state around the existing stage request, then success only after its existing API validation succeeds, or failure if that request rejects. No invented percentage or per-aircraft byte rate is displayed. Existing toasts, command gating, payloads, transport and backend behavior are unchanged. Native dialog focus handling, Escape dismissal and reduced-motion support are retained.

Verified using an isolated simulated endpoint: positive/zero traffic, service loss, heartbeat wait, aircraft connecting, upload pending, upload acknowledgement and upload failure. No flight commands were sent. Backend/launcher hashes match the pre-GUI baseline.


### Spectrum glass panels and GPS map presentation

`css/spectrum.css` supplies the earlier palette, now overridden by `css/crystal.css`: medium graphite working surfaces, darker navigation, transparent glass and independent blue, green, violet, coral and cyan panel accents. `js/spectrum.js` adds vector heading icons and finite panel-opening animations; motion respects the operating system reduced-motion preference. The balanced variant lightens the original dark pass without returning to gold surfaces.

`js/fleet-map.js` consumes the existing fleet/state refreshes through guarded callbacks. It adds detailed quadrotor SVG markers, labels, short trails, reported heading, coordinate popups and automatic fleet bounds. Manual panning, mouse-wheel zoom, aircraft focus, or KML planning disables automatic fitting. Existing map clicks, KML drawing, mission generation and flight commands retain their handlers. A neutral world view replaces the previous assumed SITL location until data arrives.

**Current backend limitation:** the existing onboard mission manager status does not publish GPS coordinates for each aircraft. The GUI therefore shows connected aircraft as `GPS unavailable`, with no guessed markers. The local state also lacks a GPS age/fix indicator, so its initialized home coordinates cannot count as a live GPS position. No backend changes were made. Actual multi-aircraft hardware tracking requires that read-only telemetry be exposed by the backend first.

The optional display contract is `drone.data.gps = {latitude, longitude, age_s, fix_type, heading_deg?, altitude_m?}`. Coordinates must be finite degrees within WGS84 ranges, `age_s` between 0 and 2.5, `fix_type >= 2`, `valid !== false`, and the aircraft must be fresh and CONNECTED. Local telemetry accepts `state.gps` with the same fields, or the existing latitude/longitude plus explicit `gps_age_s` and `gps_fix_type`. These are display inputs only, not a new endpoint or a command interface.

Verified using isolated simulated endpoints: no markers without GPS, three independently positioned aircraft, coordinate movement, heading changes, exact coordinate popup, stale-aircraft removal, and manual camera control. GPS validation checks cover stale/missing/invalid fixes and rejection of initialized home coordinates. Hardware GPS tracking has not been tested and is unavailable with the current fleet status shape.
